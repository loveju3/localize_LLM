# 文件問答專案：需求與初期架構共識

整理日期：2026-10-01。本文為目前討論共識與實作建議，不代表問答功能或雲端資源已完成部署。

更新：第一版程式已開始實作；最新模型／跨機器共用決策見 [補充文件](shared-cloud-design.md)，可用功能與限制見 [操作說明](getting-started.md)。雲端服務尚未部署。

## 目標與優先順序

1. 使用開源 LLM 分析文件並回答問題，回答可靠且可核對來源。
2. 使用 vLLM 提供雲端模型推論服務。
3. 後續建立比較模型、prompt engineering、RAG 與 LoRA／微調的實驗流程。

RAG 是檢索增強生成，prompt engineering 是提示設計；兩者不一定修改模型權重。LoRA 則是參數高效率微調方式。vLLM 負責推論，訓練需使用另外的工具。

## 初期架構

```text
PDF → Mac 解析、切段、產生 embedding
       ├─ 原始文件 → Cloudflare R2
       └─ 原文片段、向量、來源位置 → Neon PostgreSQL / pgvector

問題 → Mac 產生 embedding → Neon 檢索相關片段
     → 問題＋原文片段＋回答規則 → 雲端 GPU / vLLM
     → 回答＋檔名＋頁碼＋可核對原文
```

Neon 與 R2 為目前選定的初期方向，仍需實際驗證容量、連線及費用。Mac 執行應用程式與文件處理；小型 embedding 模型先在本機運行。生成回答的 LLM 在雲端 GPU 運行。

向量用於尋找相關內容，並不取代生成時所需的文字。雲端 LLM 會接收問題及檢索出的原文片段，通常不必接收整份文件。若日後改用雲端 embedding，建檔文字也會傳到該服務。接受雲端算力不等於已確認所有內部文件的雲端處理權限。

## 文件處理與回答品質

- PDF 優先抽取文字，保留標題、段落、表格上下文、年份、單位與註腳。
- 保留 PDF 頁序；文件印刷頁碼若能辨識，另行記錄，避免兩者混淆。
- 掃描頁需要 OCR；第一階段先偵測並提示，不將空白抽取結果當成功。
- 採向量與關鍵字混合檢索的方向；中文斷詞與檢索品質需以實際文件驗證。
- 回答須有來源支持，證據不足時明確說明；引用存在本身不代表答案正確。
- Word 後續保留標題與段落位置；Excel 保留工作表與儲存格範圍。
- Excel 加總、比較與跨表分析需程式計算，不能僅依靠文字檢索。

## 雲端 GPU 與成本

第一版採集中使用：啟動 GPU → 載入模型與 vLLM → 完成問答／評估 → 關閉資源。租用 GPU 的運行時間可能持續計費，即使沒有 API 請求。

建議預算配置為 GPU NT$450、其他費用與緩衝 NT$150；此為目標配置，不是報價或成本保證。需一併計入模型下載、啟動、磁碟、儲存、稅費與匯率。Neon／R2 優先控制在免費額度內，但仍需確認最新方案與實際用量。

部署時加入閒置關機、單次最長運行時間及用量紀錄；通知不能代替關機。關閉 GPU 後也需檢查磁碟等殘留資源費用。Serverless 縮到零作為後續選項，需比較冷啟動與總成本。

雲端 GPU 供應商、LLM、embedding 模型與量化方式尚未定案。不能保證此預算可供全天候服務或頻繁微調。

## 評估與後續擴充

先建立 20～30 題測試集，包含直接查找、跨段整理、表格數字與無答案問題。記錄檢索命中、回答正確性、引用支持程度、拒答行為、延遲及成本。

先改善解析、檢索與 prompt；有明確行為／格式需求及訓練資料後再做 LoRA。訓練按次租用 GPU，與推論分開排程。R2 可存 adapter，但應一併記錄基礎模型版本、訓練設定、資料版本與評估結果，以利重現。

內部試用依賴 Mac 保持運行。未來對外服務時，將應用與文件處理搬到雲端，加入登入、文件權限、配額、佇列與成本控制。檢索前即須限制可讀文件；僅靠回答階段隱藏內容不足以隔離資料。

## 本次環境建置範圍

建立本機 Python 虛擬環境及文件解析、embedding、Neon、R2、HTTP API 的基礎依賴。提供設定範本與離線環境檢查。尚未下載模型、建立雲端帳號／GPU、上傳文件或實作完整 RAG。
